# @cmdless/ui-sdk

Shared types and helpers for building on cmdless UI. Everything a consumer or a `@cmdless/ui-runtime` build needs, split by where it runs.

## Exports

- **`@cmdless/ui-sdk`** — platform-agnostic.
  - `Params`/`ShowParams`/`MessageBoxParams` types, `cmdlessIPC` (the [`@cmdless/rpc-sdk`](../rpc-sdk) protocol definition shared between a window's preload and the Electron main process - main ↔ renderer only, not a consumer's own backend), `createElectronIPC`, and a small typed `Emitter` used internally.
  - `defineApp(({ tool, z }) => ({ name, description?, tools }))` — an app's schema: just names, descriptions, and zod input/output shapes for each tool (both must be object schemas - MCP tool inputs are always a top-level dictionary, and `@modelcontextprotocol/sdk` requires structured output to be object-shaped whenever an `outputSchema` is declared). No handlers live here - `z` is passed into the callback so consumers don't need their own zod dependency. A tool can optionally carry its own `protocol` (an `@cmdless/rpc-sdk` `RpcProtocol`) for the rare case where its UI needs a live, bidirectional channel back to its handler, on top of the one-shot MCP input/output.
  - `runtimeSpec` — `ui-sdk`'s own app schema: `show`/`messageBox`, the same shape as `ShowParams`/`MessageBoxParams` below. Backs `ui-sdk`'s own bin (see below), not `@cmdless/ui-runtime` itself.
- **`@cmdless/ui-sdk/node`** — for the process invoking cmdless UI (or the Electron main process handling it).
  - `createApp({ spec, setup, startup? })` — turns an `AppSpec` into a runnable app. `setup()` is called once per instance and returns the tool handlers (a factory rather than a plain object, so handlers can close over per-instance state); `startup(app)` runs when the CLI is invoked with no subcommand (e.g. "just launch the window"). Returns a **factory**, not an instance - a consumer's own `src/node/app.ts` does `export default createApp({...})`, and whatever loads it (a bin entrypoint, a vite plugin's dev-mode HMR) calls it to get a fresh `App`: `{ spec, tools, cli(), run(argv?), mcp() }`.
    - `tools` - the handlers, callable directly in-process.
    - `cli()` - the generated Commander program (`tool <name> [json] [--flags]`, and `mcp`). `<name>`'s input is an optional JSON positional merged with `--field` flag overrides - scalar fields (string/number/boolean/enum) become plain flags, and object/record fields also become flags, parsed as JSON (e.g. `--config '{"reasoning":"high"}'`).
    - `run(argv?)` - `cli().parseAsync(argv)`.
    - `mcp()` - starts the MCP server on a plain WebSocket (not one of MCP's standard transports) and returns `{ address, dispose() }`, for embedding without going through argv. The CLI's own `mcp` subcommand speaks standard MCP stdio when run normally (e.g. by an external MCP client like Claude Desktop), and switches to this WebSocket form only when launched with an `'ipc'` channel present (i.e. by `runAsMcp` below).
  - `runAsMcp(importMeta, packageName, version?, cmdlessRoot?)` — resolves a package (locally via `findLocalBinPath`, falling back to `ensurePackage`'s cache) and spawns its `mcp` subcommand with an `'ipc'` stdio channel, returning `{ address, dispose() }` once the child reports its WebSocket address back. Used by an Electron main process to mediate a renderer's request for some package's MCP server, since a renderer can open a WebSocket but can't spawn a process or speak stdio itself.
  - `CmdlessUI` dispatches `show`/`message-box` requests — by default by spawning `@cmdless/ui-runtime` (via `runAsRuntime`), or with a custom `dispatch` for handling a request in-process (e.g. a window's own preload asking for a nested dialog).
  - `createShowCommand({ params, result?, dispatcher?, cmdlessRoot?, transport? })` — the usual way to build a one-off "show a window" CLI command: takes a `params(input)` callback that returns the `ShowParams` to use, and returns an `(input, parent?) => Promise<Out>` function. If a dev server has published its own URL via `setCmdlessUrl` (see below), it always overrides `params()`'s `type`/`source` - individual commands never need to check for that themselves. Pass `transport` to also stand up a `@cmdless/rpc-sdk/ws/node` server per invocation and pass its address through as `--address`, for a renderer that needs to talk directly to this process. That server only admits connections presenting the per-invocation token included in the address (`?token=`), so other pages and processes on the machine can't reach it - a renderer just connects to the address as given.
  - `getCmdlessRoot`/`setCmdlessRoot`, `getCmdlessApp`/`setCmdlessApp`, `getCmdlessUrl`/`setCmdlessUrl` — accessors for cmdless's environment, so callers never read `process.env` themselves. Each setter writes to this process's env, or to an env object passed in for a child about to be spawned. A dev-mode Vite plugin (see `apps/agent-runner`'s `vite.config.ts` for the pattern) can publish its dev server's URL with `setCmdlessUrl(url, env)` before spawning a consumer's bin, so `createShowCommand` picks it up automatically instead of the built renderer.
  - `BinChannel` — a small socket-based protocol (built on `@cmdless/rpc-sdk`'s Node socket transport) for a bin process to talk to a long-running child it spawns (e.g. Electron), without using `child_process`'s `'ipc'` stdio channel - that combination is a documented source of Electron `app.whenReady()` hangs ([electron/electron#17044](https://github.com/electron/electron/issues/17044)). Call `BinChannel.start(onMessage)` in the parent *before* spawning (fold its returned `env` into the spawn call), and `await BinChannel.connect()` at the top of the child to get a `send(message)` function back.
  - Package-caching helpers: `ensurePackage`, `runAsPackage`, `runAsRuntime`, `runPackage` (blocking, captures stdout once the process exits), `spawnPackage` (non-blocking, inherited stdio - for a long-running process like Electron where you don't need to read its output), `spawnAsPackage(importMeta, packageName, args?, options?)` (non-blocking, piped stdio - for a long-running process you need to stream to/from, e.g. a JSON-RPC-over-stdio child), `findLocalBinPath` (resolves a package's `bin` entry to an absolute path via `findPackageJSON`, given the caller's own `import.meta`).

## Its own bin

`ui-sdk` ships a `ui-sdk` bin (`npx @cmdless/ui-sdk ...`), built from `runtimeSpec` the same way any consumer builds their own app with `createApp`. Its `show`/`messageBox` handlers just forward straight through to the existing `CmdlessUI` + dispatcher (spawning `@cmdless/ui-runtime` via `runAsRuntime`, same as always) - this carries no behavior of its own, it's a schema/CLI/MCP front door onto what already happens for every dispatch. The point: `npx @cmdless/ui-sdk mcp` is a standalone, generic MCP server - "show the user a window", "show the user a dialog" - that any MCP-speaking client (an ACP agent, Claude Desktop, anything) can be pointed at directly, independent of any specific app. `@cmdless/ui-runtime` itself is untouched by any of this.
- **`@cmdless/ui-sdk/browser`** — for code running in a cmdless-hosted window.
  - `createClient(spec, { name, version })` — a facade over an app's MCP server, from the renderer. Returns a factory `(cmdless) => { spec, tools }` where each `tools[name]` matches `App<T>.tools[name]`'s shape, but lazily connects over MCP (via `window.cmdless.ipc`'s `mcpAddress` request, mediated by Electron main) the first time any tool is actually invoked. Since it only captures data until that factory is called, this is safe to export from a consumer's own `/shared` code - `export const client = createClient(spec, packageJson)` - for another app to import as a sibling dependency, or for the app itself to use on its own tools.
  - `createRenderer({ client, tool, apps? })` — the renderer side of one specific tool. `tool` (a value off that app's own `spec.tools`) gives the renderer its name/description and, if that tool declared a `protocol`, connects it over `cmdlessIPC`'s `connectionInfo` handshake (exposed as `.rpc`). `client` is the renderer's own app (its other tools, via MCP); `apps` is a `Record<string, ClientFactory>` of sibling apps' `createClient` exports, connected the same way and exposed at `.apps[key]`.
